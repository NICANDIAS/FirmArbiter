# FIRMARBITER Phase 1 Candidate-Coupling Inventory

**Source audited:** uploaded `firmarbiter_v10` repository snapshot.  
**Purpose:** classify shared-code assumptions before designing Adapter Contract v1.

## Executive conclusion

The prototype has a usable neutral skeleton—candidate discovery, generic run scheduling, Docker orchestration, external probes and result aggregation—but the current interfaces are not scientifically neutral. The highest-risk coupling is not merely named `if` statements: it is the use of candidate console text as lifecycle truth, implicit input transformation, universal runtime privileges, and result semantics that convert setup failures or unattempted probes into candidate failures.

### Immediate P0 decisions

1. Do not repair FirmAE reachability by adding another phrase, delay or special case.
2. Remove late-log promotion of boot success; a historical claim cannot recreate a live lifecycle state.
3. Freeze firmware presentation semantics before any more candidate comparison.
4. Separate setup, candidate claim, independent measurement and cleanup remediation in both execution and result schemas.
5. Build Adapter Contract v1 before refactoring runtime code.

## What should remain in the neutral core

- Discover adapter packages without knowing candidate names.
- Validate a versioned manifest and compatibility range.
- Create an immutable per-run workspace and runtime handle.
- Enforce the experiment timeout/resource/permission policy identically.
- Receive and validate structured adapter events without treating them as independent truth.
- Schedule independent probes, request shutdown, escalate termination and assemble a validated result.


## Candidate-local work that is legitimate

- FirmAE database/scratch reset and its partition compatibility patch.
- FIRMADYNE PostgreSQL provisioning, Sasquatch/compiler compatibility, makeImage cleanup fix, native pipeline translation and endpoint extraction.
- EMBA installation constraints and native command translation.
- Candidate-native console parsing, provided it occurs only inside the adapter and is translated into standard events.


## Phase 1 exit criteria

- Every shared candidate-name reference has an assigned removal/migration destination.
- Input transformation is frozen and documented.
- The old five-firmware FirmAE outputs, logs and current repository state remain preserved.
- No new candidate-specific patch is added to shared code.
- Adapter Contract v1 can be written without relying on current `success_signals`, `firmarbiter_boot_ip.txt`, or `candidate.conf` semantics.
